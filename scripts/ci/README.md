# scripts/ci

`run-ci-d.sh` runs the checks of CI. A check is one script under `scripts/<run>/ci.d/`. A unit that adds a check adds a file there and edits no line of `.github/workflows/ci.yml`.

## Commands

Start each command at the repo root.

| Command | What it does |
|---|---|
| `sh scripts/ci/run-ci-d.sh <job>` | Runs every script whose `# jobs:` line names `<job>`, in lanes (see Checks at the same time). A job is `macos` or `windows`. |
| `sh scripts/ci/run-ci-d.sh <job> --self-test` | Runs the driver's own cases and the self-test of each of those scripts, several at a time (see Self-tests at the same time). |
| `sh scripts/ci/run-ci-d.sh <job> [--self-test] NAME...` | Runs only the named scripts. A NAME is the file name without `.sh`. With `--self-test`, the name `run-ci-d` stands for the driver's own cases. |
| `sh scripts/ci/run-ci-d.sh --list [<job>]` | Prints the path of each script in the order of the run. |
| `sh scripts/ci/run-ci-d.sh --rules` | Prints one line for each script: `<NN-name> (<jobs>): <rule>`. |

Each job of `ci.yml` has the steps `ci.d self-test` and `ci.d`, which run the first two commands.

The driver's own cases run the driver inside themselves, and such a run knows it by the nested switch, a word (`yes`, `fail`, `slow`, `hold`, `late`, `gap` or `wgap`) that the own cases hand it on file descriptor 9. The driver reads descriptor 9 once when it starts and closes it for every script and every case that it starts. It refuses the variable `RUN_CI_D_NESTED` whenever it is set, the empty value included, in both steps and before anything else, also when the caller sets `RUN_CI_D_WORKER`: it prints `FAIL run-ci-d (RUN_CI_D_NESTED is set; the driver refuses it, also when it is empty)` and exits 1, so a value left in the caller's environment cannot make the own cases stop after their first case and pass. A caller that opens descriptor 9 itself with such a word is no slip, and the driver does not hold it (contract C16 point 9).

The own cases run on both systems except those on the driver's list of cases for the macos job alone (`own_macos_alone` in `scripts/ci/run-ci-d.sh`, each with a word for its reason): on a Windows host, which the driver knows by `command -v cygpath`, once, such a case makes no fixture and prints `case run-ci-d/<name> not-run (macos alone: <reason>)` in place of its verdict. A case that a probe of the host gates off prints `case run-ci-d/<name> not-run (<reason>)` in the same place: the cases of a link where a link is a copy, the Windows form of the root where there is no `cygpath`, a run directory renamed by letter case alone where the file system keeps letter case apart, the five cases of a setting that git reads by its stat data where git runs under `cygpath` (the fifth: `global-check-stat-of-a-script-in-a-home-of-its-own-leaves-the-index-read-of-the-driver`), the TMPDIR that cannot be removed or the one under a read-only parent by what a directory of mode 555 takes on the host, the two cases of `chflags` where there is none, several self-tests at a time where there is one processor, and for each signal that a script sends itself the form of the case that the host's sh does not take. A second list (`own_windows_rules`) names each rule that can differ on a Windows host with the cases that hold it there, and the own case `lists-of-the-macos-alone-cases-and-of-the-windows-rules` fails when a name of the first list is no case that the run reaches, when a case stands on both lists, when a rule has no case that runs on a Windows host, or when the gate runs a case of the first list on a Windows host; it prints the counts of the lists' Windows form on any host. The first list holds 32 cases and moves four subjects off the windows runner. How the cargo lane, the free lane and the alone part run beside each other and one after the other is not shown on the windows runner. How the driver reads a self-test's pass line, its exit code and its count of rejected fixtures is not shown on the windows runner. The place of a refusal in the recap is not shown on the windows runner. A script that is skipped in CI or outside it, and a run that goes on after a failure, are not shown on the windows runner. Each own case prints `case run-ci-d/<name> case-seconds=<n>` after its verdict, counted from the verdict of the case before it in its job, so that its fixture counts. The own cases run as two jobs (see Self-tests at the same time), and each job prints `run-ci-d own cases, job <j> of 2: <n> cases, <s> s`: those lines, not the time of the recap line, which the other self-tests decide, are the own cases' figures. Before the two jobs the one entry printed `run-ci-d own cases: <n> cases, <s> s`; in run 43783479213, the windows job alone at driver-2's commit d041893e, it read 795 s for 264 cases, of which the cases now on the first list took 127 s.

## A script

- Its path is `scripts/<run>/ci.d/NN-name.sh`: two digits, then a name of `a-z`, `0-9` and `-`. The directory of R1 is `scripts/r1/ci.d/`. No two scripts have the same `NN-name`.
- Its first ten lines hold one line `# jobs: <job>[ <job>...]` and one line `# rule: <one sentence>`. The rule is the sentence that `--rules` prints. They may also hold the line `# self-test: alone`, which makes its self-test run alone. They may also hold one line `# lane: free` or `# lane: alone`, which puts the script in the free lane or in the alone part of the step `ci.d` (see Checks at the same time); a script with neither runs in the cargo lane. They may also hold one line `# limit: <n>`, a whole number of seconds from 1 to 999999999 with no leading zero, which raises the script's time limit (see below); a carriage return at its end does not count, as for the lane line, and a limit line after line 10 is not read.
- The driver starts it in the repo root as `sh <file>` or `sh <file> --self-test`, with no standard input, through `perl`, which gives it a process group of its own and sets INT and QUIT to their defaults. A background job of a shell starts with INT and QUIT ignored, and no shell can undo that, so without this start a script could not show what it does on an interrupt. A script therefore meets INT, QUIT, HUP and TERM as it does in the foreground on that system, in both steps, several at a time and alone; on the windows runner the sh of Git Bash runs on after a QUIT that it sends itself, also in the foreground, so a script there does too. The driver fails with `FAIL run-ci-d (perl does not run; ...)` when `perl` does not run.
- A script that runs longer than its time limit fails with `FAIL <NN-name> (time limit <n> s)` in the step `ci.d` and with `FAIL self-test:<NN-name> (time limit <n> s)` in the step `ci.d self-test`. The driver sends TERM to the script's process group, and KILL to the group 5 seconds later when a process of the group is still there. Its own case for a script that ignores TERM gives that script a limit of 5 s and fails when the run takes more than 40 s: the ceiling tells a run that ends within 40 s from one that does not, such as a run under a driver that sends neither KILL, where the script sleeps its 60 s; it does not tell which signal ended the script. An own case that is held to a ceiling prints `case run-ci-d/<name> seconds=<n> max=<ceiling>` after its verdict line. When the caller sets `CI_D_SCRIPT_LIMIT_S`, its value is the limit of every script and of the driver's own cases (the name `run-ci-d`), which then fail with `FAIL self-test:run-ci-d (time limit <n> s)`. Without it, a script's limit is 1,200 seconds, or the number of a line `# limit: <n>` among its first ten lines when that number is higher, in both steps; the own cases' limit is 1,250 seconds, for each of their two jobs. The own case that runs starts its witness and its nested driver each through perl, which makes the process's group, writes the process's number into a record of its own and then reads a mark; each job of the own cases has its records and its mark in a directory of its own. At a job's limit the driver writes that job's mark, then reads the job's two records and ends the groups that they name, then the job, and empties both records after it has waited for the job's process. So a record names only a group that exists, and a witness or a nested driver that the driver's read of the records missed finds the mark, empties its record and ends before it runs on, so neither outlives the step (a windows run once left a nested driver that its case started after the driver had read the records). At its end the case ends its witness, then empties the witness's record, then waits for it.
- The margin of these limits. The default of 1,200 s was set at about 1.5 times the longest time of 15-gate-self-test then measured in the step `ci.d` of hosted macos jobs (773 to 804 s; ruling MS-1 (g)), and it is below the 1,801 s that 30-mutants took on main's macos job at 105125b2 (run 43547657512). A runner that is slower than a script's measured time by more than its margin fails the script with no fault in it. 12-test and 15-gate-self-test name `# limit: 1800`, at least 1.5 times the longest hosted times that were measured when the line was set: 902 s for 12-test in the step `ci.d` of the windows job in the hosted runs of land-44 (ruling PL-25, Addition 1), and 887 s for 15-gate-self-test in that of the macos job in run 43724550260 (ruling PL-26, Addition 1). 30-mutants names `# limit: 1900` (ruling WS-7). A push to main runs its budget pass, which starts no row after 240 s, after its apply-only pass, and in main's push run 44151327847 at 5c97fcd6 the driver ended it at its limit of 1,200 s after 1,208 s, so its whole time on that push is above 1,200 s and not known; 1.5 times 1,208 s is 1,812 s. The 1,801 s of run 43547657512 does not set that margin: at 105125b2 the apply-only pass built the mutant of each cargo row with cargo build, and since b3eb47f6 (mutants-4) it type-checks a cargo row with cargo check. On a push to main the budget pass took 256 to 297 s in six hosted macos jobs, and the longest whole run of 30-mutants on such a push was 993 s, which held an apply-only pass of 730 s and a budget pass of 259 s (main's push run 44088333598 at 37955abc); the longest measured figure, 1,208 s, is a floor, as is the 1,201 s at which the driver ended the apply-only pass alone at 03175fb8, the runner of mutants-7 (run 44220704147), and 1.5 times 1,201 s is 1,801.5 s; that code is not on main, and on a push to main it would add its budget pass, at least 1,201 s and 256 s, 1,457 s, which asks for at least 2,185.5 s, so the runner of mutants-7 comes to main with its apply-only pass made as short as before or with a new limit (ruling JB-52, point 3). The job's limit is 180 minutes, 10,800 s, since ruling WS-9, which raised it because main's push run 44373816491 at 68c80599 read 8,342 s in its windows job; it was 150 minutes, 9,000 s, by ruling JB-52, and the figures of this paragraph are read against those 9,000 s. In the macos jobs of land-56 at b3581355 the other checks read 6,486 s less 758 s of 30-mutants, 5,728 s (push run 44201520845), and 5,859 s less 724 s, 5,135 s (pull request run 44201553968); 15-gate-self-test failed its first pass there at 583 and 587 s and ran no dash pass, and with both passes at their longest measured time in their place, 913 s (job 133835438276 of main at 760a75b0), the other checks read 6,058 s and 5,461 s. With the limit of 1,900 s that is 7,958 s and 7,361 s, 1,042 s and 1,639 s under 9,000 s; a green push to main also runs the save of the Rust cache and the step Lockfile unchanged, which the failed push job skipped (102 s and 6 s in main's push run 44088333598), and so reads 8,066 s, 934 s under 9,000 s; against the 7,200 s of 120 minutes the push job read 7,628 s with the limit before any dash pass. The three run in the alone part of the step, so no two of their limits are spent at once. A case of the own cases holds that these three scripts, and no other script under a `ci.d` directory, carry a limit line. So a script whose longest measured hosted time passes 800 s (the default less its margin of 1.5) names its own limit with `# limit: <n>`, at least 1.5 times that time, and its owner shows that the limit, with the other checks of the job as last measured, stays under the job's limit: the key `ci_job_timeout_min` of `docs/baseline/r1-gate-bounds.txt`, in minutes. The driver reads neither that key nor any other source of the job's limit, so it takes a limit line above the job's limit, and a hang of such a script ends as the job's timeout with no named line. The own cases' 1,250 s is 1.5 times the larger of two hosted figures of their own entry's line in the step `ci.d self-test` of the windows job, beside the other self-tests, rounded up to the next 50 s (ruling PL-30 point 2): 832 s for 233 cases in run 43794356145 at driver-2's commit 45deef62, whose runner's processor model the run did not print (its step Processor was skipped after the step `ci.d self-test` failed), and 821 s for 233 cases in run 43806940402 at driver-2's commit 3b59ec8a, on a runner whose step Processor printed `processor: Intel(R) Xeon(R) Platinum 8370C CPU @ 2.80GHz; identifier: Intel64 Family 6 Model 106 Stepping 6, GenuineIntel; processors: 4`; 1.5 times 832 s is 1,248 s. The value is never 1,200 s, the default, so that the line that gives the own cases a value of their own cannot go with every case passing. It was 1,100 s before (ruling PL-29 point 5: 1.5 times the 668 s that the table of run 43783479213, the windows job alone, gave the cases that run on windows, with no other self-test beside them), and 2,800 s before that, three times the 916 s that the recap line of the step `ci.d self-test` read in the windows job of run 43683245897, a time that the other self-tests decide; the own entry's line holds the own cases' seconds alone. A process that the script started into a process group of its own is not ended at the limit.
- When a script has ended, the driver ends what is left of its process group in the same way: in the step `ci.d` at once, before it removes the `TMPDIR` and reads the tracked files; in the step `ci.d self-test` at the end of the step, for all self-tests at once, in one process: the driver waits up to 5 seconds for the groups that the self-tests left to end, then sends TERM to each group that is still there, and KILL 5 seconds later, so that a late line on standard error still reaches the log; the wait is the same for one such self-test as for several. A process that the script started into a process group of its own is not ended at the script's end.
- The driver sets `CI_D_REPO` (the repo root), `CI_D_JOB` (the job), `CI_D_ARTIFACTS` (the directory `target/ci-artifacts/<NN-name>/`, which the driver makes), `LC_ALL=C`, and `PATH` with the cargo bin directory first. Every other variable of the caller whose name holds no lower-case letter passes through; the driver also sets `RUN_CI_D_WORKER` for its own use. The driver's own commands run on the caller's `PATH` without the cargo bin directory (an entry that is the same string as `$CARGO_HOME/bin` once trailing slashes are cut on both, or that `test -ef` finds to be the same directory), so a tool that a script puts there answers for the scripts after it and not for the driver. The driver runs its own git with no global git configuration (`GIT_CONFIG_GLOBAL=/dev/null` and no global attributes file) and with no variable of the caller whose name starts with `GIT_` (the names are read once when the driver starts); a setting that a script writes into the global configuration, or that the caller gives in such a variable, holds for the scripts and not for the driver's reads. A script and an own case get the caller's environment as before, the `GIT_` names included. The system's git configuration, which carries `core.autocrlf` on the windows runner, comes from git's install prefix and is read as before. The own case for a global `core.checkStat minimal` with an edit of the same size and the old modification time does not run on the windows runner, where git reads no inode and a creation time that a write leaves as it was, so the default read does not see such an edit either.
- The last line that it prints on standard output and its exit status give the result:

  | Last line | Exit status |
  |---|---|
  | `PASS <NN-name>` | 0 |
  | `FAIL <NN-name> (<cause>)` | 1 |
  | `SKIP <NN-name> (<reason>)` | 77 |

  For any other status, or a last line that does not match the status, the driver prints `FAIL <NN-name> (exit <n>)`. In CI, where `CI=true`, a SKIP is a failure: a script installs the tool that it needs or fails.
- With `--self-test` it runs its own check on fixtures that it carries. At least one fixture must fail. Its last line is `PASS self-test:<NN-name> (<k> failing fixtures rejected)` with exit status 0, or `FAIL self-test:<NN-name> (<cause>)` with exit status 1. The driver fails a script whose `k` is 0.
- The driver gives it a `TMPDIR` of its own in both steps, a new empty directory, and removes that directory after the script, whatever its status. Each script's `TMPDIR` is the one entry of a parent of its own, and those parents are the only entries of one directory that the driver makes for them, so `$TMPDIR/../..` is shared by all scripts. After a script the driver removes its `TMPDIR` alone: a script that closes its parent is named with the line below and the next script runs, and the parents go when the driver removes that directory at its exit. The driver keeps its own files (its reads of the tracked files, each script's output and status, the recap) in another directory, which holds no `TMPDIR`, so a script that writes the files of the directory that holds its `TMPDIR`, or of the directory above that, does not reach them. In the step `ci.d self-test` the driver removes a self-test's `TMPDIR` at the end of the step. The driver tries each removal up to three times, one second apart, so about 2 seconds in all, because on Windows a native program or a scanner can keep one removal from taking the whole directory. When the directory is still there after the third try, the script fails with `FAIL <NN-name> (its TMPDIR cannot be removed)`, or `FAIL self-test:<NN-name> (...)` in the step `ci.d self-test`. The driver's own cases show both lines with a file that the case makes user-immutable with `chflags` and makes removable again on every way out; on a system without `chflags`, the windows runner among them, those cases do not run and the lines are not shown there. When the driver exits, it removes its own temporary directory.
- It writes only under a directory from `mktemp -d` with a template under `$TMPDIR` and under `CI_D_ARTIFACTS`. A script that makes a temporary directory anywhere else removes it by its own trap on EXIT, INT, TERM and HUP. It changes no tracked file and builds with `--locked`.
- The driver holds the rule on tracked files. It reads `git status --porcelain --untracked-files=no` against an index of its own, which it makes from HEAD and refreshes before the first script, so stat data that a script writes into the checkout's index hide no change; before the first script it also reads `git status` once against the checkout's own index, with `--no-optional-locks`, and a path that either read reports fails the run as a tracked file that differs from HEAD before the first script (that read goes into no later comparison, so no script is named for it); the paths whose entries in the checkout's index differ from HEAD (`git diff-index --cached`); the entries of `git ls-files -v` that are marked assume-unchanged or skip-worktree, the commit of HEAD, a hash of the settings that git reads for the checkout (the output of its own git's `config --list --show-origin`, files that the configuration includes and `config.worktree` with it; the driver keeps the hash alone and never prints or stores the listing, which holds the checkout's token), the content of `info/attributes` and the replace refs, before the first script, after each script of the step `ci.d`, and after the step `ci.d self-test` as a whole, whose self-tests run at the same time. Each entry that a script or the step changed fails the run with `FAIL run-ci-d (<NN-name> changed a tracked file: <path>)` (`one of <NN-name>, <NN-name>` when other scripts ran beside it; see Checks at the same time), `FAIL run-ci-d (the step ci.d self-test changed a tracked file: <path>)` `FAIL run-ci-d (<NN-name> moved HEAD)` or `FAIL run-ci-d (<NN-name> changed the git settings of the checkout: <config, info/attributes or the replace ref>)`. A tracked file that already differs from HEAD before the first script fails the run with `FAIL run-ci-d (a tracked file differs from HEAD before the first script: <path>)`, and one marked assume-unchanged or skip-worktree with `FAIL run-ci-d (a tracked file is marked assume-unchanged or skip-worktree before the first script: <path>)`; no script is named for it, nor for a later change of such a file that leaves its line of `git status` as it was. After a script has changed a tracked file, the driver goes on with the scripts that run and that are still to run, on the checkout as it was left; the run fails, and a PASS line after such a line says nothing about the committed tree. What a process that a script started into a process group of its own writes later is seen at the next read and named for the script or scripts that ended since the read before it, which need not hold the writer; what it writes after the last read fails the next run before its first script, with no script named.
- It prints counts, sizes, times and booleans only, because the logs of CI are public.
- It does not depend on another script having run.

## Limits that a script meets

- The rule on tracked files holds a script that writes the checkout by mistake. It does not hold a script that writes the driver's own files, whose directory stands beside the directory of the `TMPDIR`s (a script can learn its path without a search, for example from the path of its own standard error), an untracked `.gitattributes` in the work tree, which git reads in the driver's read as well and which can hide a re-encoding of the same size, a tool that it puts earlier on the `PATH` of the scripts after it (the cargo bin directory among them), the system's git configuration, `.git/info/grafts`, `.git/info/exclude`, a hook under `.git/hooks`, the job's environment files, or a change that is put back before the script ends; each of these is plain in a diff and is read at the landing.
- The windows job checks out the repository with depth 1, and the macos job checks it out with its whole history. A script that names the job `windows` reads no history: `git log` shows one commit, and a merge base or a diff against another commit fails there.
- The case `standin-strict-run-alone` of `check-cost.sh` and `check-memory.sh` counts the processes named `halvo-capture` on the whole machine with `pgrep`. It fails when another self-test of the R1 gate runs beside it, because that self-test starts its own stand-in under the same name. Run the gate's self-tests one at a time on one machine.
- A native Windows program reads `TEMP` and `TMP`, not `TMPDIR`, so what it writes there stays outside the `TMPDIR` that the driver removes. A signal of the driver does not reach a native Windows program, such as `cargo.exe`, that a script started; such a program can run on after the time limit and after an interrupt, and can hold the lock of the build directory.
- `target/ci-artifacts/12-test/tests.txt` holds the Running and Doc-tests lines and the test result lines of 12-test's `cargo test` run. It is no proof by itself that 12-test ran in the same driver run or passed: an earlier run can have left it, and a test's child can print lines of the same form. A script runs no crate's tests that 12-test runs, unless it reads that file first and runs them only when the file is missing, or its jobs line names windows alone (contract C16, point 18). 12-test runs in the alone part of the step `ci.d`, after every script of the first part, so a script of the first part never finds the file of the same run: in a fresh checkout the file is missing when it reads it, and it runs the tests itself.

## Self-tests at the same time

With `--self-test` the driver runs the step in two parts. The first part runs the driver's own cases and every self-test that does not run alone, up to `CI_D_SELF_TEST_JOBS` at a time. Without the variable it runs as many as the machine has processors (`getconf _NPROCESSORS_ONLN`, else `NUMBER_OF_PROCESSORS`, else 1). The second part starts when every job of the first part has ended, and runs each self-test that runs alone, one after the other in the order of the run, with nothing beside it. The two parts took about 320 to 397 s off the step `ci.d self-test` of the windows job (verifier-1 of the CI-time run: 387 s on the one pair of one processor model, across runs, with the runner's speed taken out, and 292 to 397 s over all pairs; pr-review-1: about 320 to 370 s against each run's own self-test seconds; the raw fall on that pair is 476 s), from runs on processor models that GitHub draws by lot; 600 s off the job is not shown. The step `ci.d` runs its scripts in lanes (see Checks at the same time).

- The own cases run as two jobs, each of them one entry of the first part with the own cases' limit (see A script). The first job runs the cases up to the case `own-cases-reach-their-limit-at-1250-s`, the second job the cases after it. The second job also goes through the setup of the first job's cases without running them, so that it reaches every case by name and its case `lists-of-the-macos-alone-cases-and-of-the-windows-rules` reads them all. A nested run of the driver inside an own case runs its own cases as one job, as before. The driver starts the two jobs first, then the self-tests that `scripts/ci/self-test-first.txt` names, in the order of that list, and then the others in the order of the run. When both jobs have ended, after the second job's lines, the driver prints the case `own-cases-in-two-jobs-print-each-case-once-in-the-order-of-the-run`. It fails when the run reaches a case name twice, when the first job printed other cases than it reached, when the second job reached the first job's cases in another order, or when the two jobs together printed other cases than the run reached. Then the driver prints one line for the own cases: `FAIL self-test:run-ci-d (time limit <n> s)` when a job reached its limit, `FAIL self-test:run-ci-d (it ended without a verdict)` when a job ended without its counts, and otherwise the PASS or FAIL line of both jobs together, with the sum of their failing fixtures rejected; its FAIL form names each wrong case of both jobs with one blank before it, `FAIL self-test:run-ci-d (wrong verdict in: <a> <b>)`, as the one job did. The five own cases whose names start with `two-job-verdict-` call that verdict on two made-up job directories, because a nested run never runs two jobs: the wrong cases of both jobs, the sum of their counts, a job at its limit, a job without its counts, and a case printed in both jobs. When a job cannot start, its line `FAIL self-test:run-ci-d (its temporary directory cannot be made)` is the one line, and the driver prints neither the case nor a second line.

- Each self-test writes its standard output and its standard error to files of their own. A self-test has ended when its script has exited and every process that holds its standard output has closed it, as in a run one at a time; its standard error does not hold the end. When a self-test and every self-test before it in the order of the run have ended, the driver prints its standard output, then its standard error as far as it is written, then its `seconds` line. A self-test that runs alone holds back the output of every self-test after it in the order of the run until it has run in the second part. So the log holds each script's lines together and in the order of the run, the byte order of the path (see The scripts root), whatever the number at a time and whatever the order of the starts, when the job reads both streams through one pipe; the workflow runs the driver without `2>&1`, and a runner that reads the two streams through two pipes can put a script's standard error after the next script's lines. What a process of a script writes on standard error after that print, in either step, the driver prints before the recap, under the line `standard error of <NN-name> after it was printed:`.
- A self-test runs alone when its first ten lines hold `# self-test: alone`, or when its name is the first word of a line of `scripts/ci/self-test-alone.txt`. The driver then runs it in the second part of the step, after every other self-test and both jobs of the own cases have ended, and starts no other self-test until it has ended. A line of the list is the name, a blank and the reason; blanks before the name and a carriage return at the end do not count. A blank line, and a line whose first word starts with `#`, is a comment. The list holds the scripts that fail beside another and that the run which owns the list may not change; the owner of such a script moves it to its own header. The driver fails the step with `FAIL run-ci-d (scripts/ci/self-test-alone.txt names <name> without a reason)` for a line that holds a name and no reason, with `FAIL run-ci-d (scripts/ci/self-test-alone.txt names <name>, which is no script)` for a line whose name is no script of any job, and with `FAIL run-ci-d (scripts/ci/self-test-alone.txt cannot be read)` when the list is there and is no file that it can read.
- `scripts/ci/self-test-first.txt` names the self-tests that start first in the first part, one name a line, in the order in which they start. It holds the longest self-tests of the windows job, longest first, so that the first part does not end on one long self-test that started late. A line of the list is the name; blanks before it and a carriage return at the end do not count, and the driver reads no word after the name. A blank line, and a line whose first word starts with `#`, is a comment. The list changes the order of the starts alone: it adds no self-test to the run and leaves none out, and each self-test's output keeps its place in the order of the run. A name of a self-test that runs alone, or of a script of the other job, starts nothing early. The driver fails the step with `FAIL run-ci-d (scripts/ci/self-test-first.txt names <name>, which is no script)` for a line whose name is no script of any job, and with `FAIL run-ci-d (scripts/ci/self-test-first.txt cannot be read)` when the list is there and is no file that it can read.
- A self-test whose job in the driver ends without an exit status fails with `FAIL self-test:<NN-name> (it ended without an exit status)`.

## Checks at the same time

The step `ci.d` runs its scripts in two parts. In the first part, the cargo lane runs every script that names no lane, one after the other in the order of the run, and beside it the free lane runs every script whose first ten lines hold `# lane: free`, in the order of the run, up to `CI_D_CHECK_JOBS` at a time. When every script of both lanes has ended and the driver has ended its group, removed its `TMPDIR` and read the tracked files, the second part runs the scripts whose first ten lines hold `# lane: alone`, one after the other in the order of the run, each with no other script of the step beside it. `CI_D_CHECK_JOBS` bounds the free lane alone. Without the variable the free lane runs as many as the machine has processors, counted as for `CI_D_SELF_TEST_JOBS`. A value that is not a whole number from 1 to 999999999 fails the step with `FAIL run-ci-d (CI_D_CHECK_JOBS=<value> is not a whole number from 1 to 999999999)`.

- Each script writes its standard output and its standard error to files of their own, and the driver prints them as it does in the step `ci.d self-test`: when a script and every script before it in the order of the run have ended, its standard output, then its standard error, then its `seconds` line. The recap holds the line of each script in the order of the run, and a script that fails stops no other. A script of the alone part holds back the output of every script after it in the order of the run until it has run in the second part, so a script that fails in the first part may print its lines near the end of the step. The lane line does not touch the step `ci.d self-test`: a self-test runs alone only by `# self-test: alone` or by scripts/ci/self-test-alone.txt.
- When a script has ended, the driver ends what is left of its process group, removes its `TMPDIR` and reads the tracked files at once, also while scripts before it in the order of the run still run. A change that it finds there names every script that ran since the last read, with the names in the order of the run: `FAIL run-ci-d (one of <NN-name>, <NN-name> changed a tracked file: <path>)`, and in the same way `one of <NN-name>, <NN-name> moved HEAD` and `one of <NN-name>, <NN-name> changed the git settings of the checkout`. That line stands in the recap after the line of the script at whose end the driver read the files; a change found at the end of a script of the alone part names that script alone. A change that a later read finds undone, after the driver reported it, is not reported again.
- A script names the free lane only when it keeps to all of this: it runs no cargo command (build, test, run, install, tree, metadata, fmt, clippy, deny or any other), so it never takes cargo's build lock; it binds no fixed port or socket path; it makes and reads no item of the login keychain; it writes nothing that another script reads or writes, and in the work tree it writes only under its `CI_D_ARTIFACTS`; it walks no directory that another script writes, such as `target/`; it depends on no other script; it counts no process of the whole machine; it starts no worker processes or threads of its own that keep several processors busy for more than a few seconds of a run with nothing beside it, so a model checker with several workers, as TLC is in the formal checks (36 to 187 s in the hosted run of main at b3eb47f6), names no lane, because on a hosted runner of 3 or 4 processors its workers take the processors that the cargo lane needs, while a tool that spreads a few seconds of work over threads or processes, as biome lint and node --test do, keeps to this; it installs no tool with a package manager; it runs no git command that writes the index of the checkout (add, update-index, stash, checkout --, reset, commit), because the driver reads the tracked files while it runs; and it leaves no process. A script that cannot be shown to keep to this names no lane.
- A script names `# lane: alone` when its verdict rests on a reading of this machine that another running script can move (a share of a processor, resident memory, a count of the machine's processes by name, or a time that it holds against a bound, a floor or a budget), or when it runs tests whose deadlines were set with the step to themselves, or when it changes a setting of the whole machine for the time of its run, such as a firewall rule that names no program or an audit setting. A script that names no lane is kept apart from cargo's builds and from nothing else. The driver keeps no other script of the step beside a script of the alone part; it does not keep away the runner's own services, nor a process that an earlier script left in a process group of its own.

## A signal to the driver

When INT, TERM or HUP reaches the driver, in either step, it sends TERM to the process group of every script that runs or has ended without the driver having ended its group (in the step `ci.d self-test` that is every self-test that it started, the list that the end of the step walks), and, after it has written the mark of each job of the own cases that it started, to the nested driver and the witness of the case that runs in each such job, as their records name them (one that the read missed finds the mark and ends), KILL 5 seconds later to a group that is still there, prints `FAIL run-ci-d (the step was interrupted by <signal>; every self-test that it started is ended)`, or `every script` in the step `ci.d`, and exits with 130, 143 or 129. In the step `ci.d` it first prints the standard output and the standard error of every script that it started and has not printed, in the order of the run. It names the scripts that it started, by their output; it does not name the scripts that never started, and it prints neither the recap nor the count line. A process that a script started into a process group of its own is not ended.

What a self-test keeps to, so that it can run beside the others: it writes only under its `TMPDIR` and its `CI_D_ARTIFACTS`, depends on no other script's self-test, binds no fixed port or fixed path, counts no process of the whole machine, installs no tool with a package manager that another self-test also installs (two `brew install` runs at the same time clashed on one bottle directory in scratch run 43269049946), and leaves no process that holds its standard output or standard error. A self-test that cannot keep to this holds `# self-test: alone`.

## What the driver prints

1. The output of each script when it has ended, in the order of the run, then `seconds <NN-name> <n>`, the script's time in whole seconds, in both steps. The `seconds` lines of scripts that ran at the same time overlap, so their sum is more than the time of the step.
2. One line for each script: the script's PASS, FAIL or SKIP line, or the driver's own FAIL line for it; and the driver's FAIL line for each tracked file that changed (see A script).
3. `ci.d <job>: <p> passed, <f> failed, <s> skipped`. With `--self-test` the line is `ci.d <job> self-test: <p> passed, <f> failed`.
4. The output of the lockfile guard, `git diff --exit-code HEAD -- Cargo.lock package-lock.json`, when a lockfile differs from HEAD, staged or not. The guard also compares the hash of each lockfile in the work tree with its blob in HEAD, so an index entry marked assume-unchanged hides no change.

## Exit status

| Status | Meaning |
|---|---|
| 0 | Every script that ran passed or skipped, at least one passed, and the lockfile guard passed. |
| 1 | A script failed, every script skipped, no script names the job, a NAME matches no script, a tracked file differs from HEAD (see A script), the lockfile guard failed, `CI_D_SCRIPT_LIMIT_S` is set to anything but a whole number from 1 to 999999999, `RUN_CI_D_NESTED` is set, also to the empty value, in the two steps, or `perl` does not run. In the step `ci.d` also: `CI_D_CHECK_JOBS` is set to anything but a whole number from 1 to 999999999. With `--self-test` also: `CI_D_SELF_TEST_JOBS` is set to anything but a whole number from 1 to 999999999, or `scripts/ci/self-test-alone.txt` cannot be read, or a line of it names no script or gives no reason, or `scripts/ci/self-test-first.txt` cannot be read, or a line of it names no script. |
| 130, 143, 129 | INT, TERM or HUP reached the driver, which ended every script that it had started. |
| 64 | Bad usage. |

The driver refuses an entry of a `ci.d` directory, prints `FAIL <name> (<cause>)` for it and counts it as failed in every job, when the entry is not a regular file (a directory or a symbolic link, also a dangling one), when its file name is not `NN-name.sh` (no `.sh` suffix, an upper-case suffix or a hidden name included), when its first ten lines do not hold exactly one `# jobs:` line and one `# rule:` line, when the `# jobs:` line names anything but `macos` and `windows`, when its first ten lines hold more than one `# lane:` line or a `# lane:` line that is neither `# lane: free` nor `# lane: alone` (a carriage return at its end does not count), when its first ten lines hold more than one `# limit:` line or one whose value is not a whole number from 1 to 999999999 with no leading zero (a carriage return at its end does not count), when git does not track it (`FAIL <NN-name> (git does not track it)`: `git ls-files` does not list it, as for a new script that is not added yet or a file that a self-test left in a `ci.d` directory for the next step), or when another script has the same name.

With no script for the job the driver prints `FAIL run-ci-d (no scripts for <job>)` and exits 1, also with `--self-test`. The one exception is `--self-test run-ci-d`, which runs the driver's own cases and needs no script.

## The weekly run

The workflow `ci` also runs on the event `schedule`, on Sundays at 03:17 UTC, on the newest commit of main. It runs both jobs with every step, and on this event the Rust cache step of each job takes the prefix key `v0-rust-cold`, so it restores no Rust build cache and saves none. GitHub's documentation says that a scheduled run may start late under a high load and that some queued jobs may then be dropped, so a Sunday without a weekly run is no fault of the tree.

The run is there for two things. A break that only a restored Rust build cache hides shows here first, and its jobs are the only measure of a job that builds everything without that cache.

A red weekly run shows in the repository's Actions list under the event `schedule`, and its jobs are checks on main's newest commit. A break that a restored Rust build cache hid is one cause of a red weekly run among several: a cold job at the limit of 180 minutes, a self-test or a script of the step `ci.d` at its time limit (1,200 s, or more by its own `# limit:` line; the driver's own cases have a limit of their own; see A script), a step that reads the event (the commit-message step on its first run of this event), a change of the runner image since the push run, a runner's failure and a flaky test. The failed job's log tells which. GitHub tells the account that last changed the cron line of the workflow file, or the account that last switched the schedule on again, as that account's notification settings for GitHub Actions choose.

No gate and no merge script reads the weekly run: `scripts/merge-pr.sh` reads the events `push` and `pull_request` alone. To mend a red run, read the failed job's log and fix the fault on a branch through a pull request, as any other fault.

When the weekly run has shown a break that a cache hid, the pull request that mends the tree restores main's same Rust cache in its own run, so its green does not show the mend. The bad cache goes when main's Rust caches are deleted, which GitHub's documentation lets an account with write access do on the Caches page under the repository's Actions tab or with the GitHub CLI (`gh cache delete`); main's next push run then builds from nothing and saves a new cache. It also goes when the restore key changes, by a change of the toolchain or of the prefix in the pinned prefix-key line, which is a ruled change of the pin; a change of Cargo.lock or of a manifest changes the cache's key but not its restore key, so the step still restores the old cache. And it goes when GitHub removes a cache that no run has read for seven days, as its documentation says. Until the bad cache goes, every run but the weekly run restores it, so the next weekly run is the first that shows the mend; once the cache has gone in one of these ways, the next run of any branch builds without it and shows the mend as well.

The lint `scripts/r1/ci.d/17-workflow-lint.sh` pins the lines of the schedule and each job's Rust cache step: a change of one of them changes the pinned text at the top of that script in the same commit, by a ruling.

In a public repository GitHub switches a schedule off after 60 days without activity in the repository. The owner switches it on again on the repository's Actions page: select the workflow `ci`, then Enable workflow.

## The scripts root

The driver lists every entry of `scripts/*/ci.d/` in byte order of the path, and the hidden entries after all others, so `scripts/r1/ci.d/` runs before `scripts/r2/ci.d/`, and it runs each entry that is a regular file named `NN-name.sh`. When `CI_D_SCRIPTS` is set, it lists `$CI_D_SCRIPTS/*/ci.d/` instead. The root may be spelled `scripts`, `./scripts`, `scripts/`, with `/.` at its end, as an absolute path inside the work tree, as a path through a link to a directory of the work tree, from a working directory that is itself spelled through a link, under a caller's `CDPATH`, and under Git Bash in the form that `cygpath -m` gives: before it compares the entries with one listing of `git ls-files`, read with `core.quotePath=false`, the driver brings the root to the listing's form by its physical path (`cd -P` into the root, with `./` before a relative root, and `pwd -P`, against `pwd -P` of the top of the work tree), so a run directory named with a letter outside ASCII is read as tracked, and a root such as `x/../scripts`, with x a link, is read where its files lie, so an untracked script there is refused under a tracked name. When the cd fails, or the physical path is not under the top, the driver reads the root by its text. A root outside the work tree lists nothing that git tracks. A root that starts with two slashes is read as with one on macOS, while the sh of Git Bash reads it as a network path that names no directory of the work tree, so there the driver finds no script and answers `FAIL run-ci-d (no scripts for <job>)`. A run directory renamed by letter case alone, on a file system that ignores case, stays refused, because git lists it under its old name. This command shows that an empty set fails:

```sh
CI_D_SCRIPTS="$(mktemp -d)" sh scripts/ci/run-ci-d.sh macos
```

## Artifacts

A script saves what a reader of a failed run needs under `CI_D_ARTIFACTS`. The last step of each job uploads `target/ci-artifacts/` as the artifact `ci-artifacts-<job>`, also when the job failed.
