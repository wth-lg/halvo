# scripts/ci

`run-ci-d.sh` runs the checks of CI. A check is one script under `scripts/<run>/ci.d/`. A unit that adds a check adds a file there and edits no line of `.github/workflows/ci.yml`.

## Commands

Start each command at the repo root.

| Command | What it does |
|---|---|
| `sh scripts/ci/run-ci-d.sh <job>` | Runs every script whose `# jobs:` line names `<job>`, in lanes (see Checks at the same time). A job is `macos` or `windows`. No run of CI uses this form: a check runs in CI when `scripts/ci/merge-gate.txt` or `scripts/ci/slices.txt` names it. |
| `sh scripts/ci/run-ci-d.sh <job> --self-test` | Runs the self-test of each of those scripts, several at a time (see Self-tests at the same time). |
| `sh scripts/ci/run-ci-d.sh <job> [--self-test] NAME...` | Runs only the named scripts. A NAME is the file name without `.sh`. |
| `sh scripts/ci/run-ci-d.sh <job> --merge-gate` | Runs only the scripts that `scripts/ci/merge-gate.txt` names for `<job>` (see The merge gate). It takes no NAME and no `--self-test`. |
| `sh scripts/ci/run-ci-d.sh <job> --slice <slice>` | Runs what `scripts/ci/slices.txt` names for the slice (`mon`, `tue`, `wed`, `thu`, `fri`, `sat` or `sun`) and `<job>`: first the self-tests, then the checks (see The slices). It takes no NAME and no `--self-test`. |
| `sh scripts/ci/run-ci-d.sh <job> --checks '<NAME> [<NAME>...]'` | Runs the named checks alone, each with its self-test first. A NAME that is a check of the other job alone is skipped with one line, and a NAME that is a check of neither job fails the call before anything starts. |
| `sh scripts/ci/run-ci-d.sh --list [<job>]` | Prints the path of each script in the order of the run. |
| `sh scripts/ci/run-ci-d.sh --rules` | Prints one line for each script: `<NN-name> (<jobs>): <rule>`. |

Each job of `ci.yml` has the step `ci.d merge gate`, which runs the fourth command on a push and on a pull request (see The merge gate), and the step `ci.d slice`, which runs the fifth command on the schedule and in a run by hand, or the sixth when the run by hand names checks (see The slices). The driver has two kinds of run: a check run, which runs checks, and a self-test run, which runs self-tests (`--self-test`). The forms `--merge-gate`, `--slice` and `--checks` are made of these two, and what the sections below say of a kind of run holds in each form. The forms `--merge-gate`, `--slice <name>` and `--checks <names>` RUN what they name: never call one with a real name on a developer's Mac, not even to see whether the name is taken; a name that the usage refuses, or a scratch clone whose list holds a name that is no check, shows a refusal and starts nothing.

The driver has no cases of its own. One control stands in their place, the red control: `scripts/ci/red-control/r0/ci.d/10-red.sh` is a tracked check that always fails, and the form `--merge-gate` first runs the driver on it alone (`CI_D_SCRIPTS=scripts/ci/red-control sh scripts/ci/run-ci-d.sh <job> 10-red`). The gate goes on only when that run exits 1 and ends with the check's line `FAIL 10-red (planned)` and the count line of the job with 0 passed; else it prints that run's output and `FAIL run-ci-d (the red control did not come out red: ...)` and exits 1 before a check of the gate starts. So each run of the merge gate, in both jobs, shows that a check which fails makes the driver's run fail. It shows nothing else of the driver: a wrong verdict for a time limit, a lane, a signal or a changed tracked file has no case since the slices.

## A script

- Its path is `scripts/<run>/ci.d/NN-name.sh`: two digits, then a name of `a-z`, `0-9` and `-`. The directory of R1 is `scripts/r1/ci.d/`. No two scripts have the same `NN-name`.
- Its first ten lines hold one line `# jobs: <job>[ <job>...]` and one line `# rule: <one sentence>`. The rule is the sentence that `--rules` prints. They may also hold the line `# self-test: alone`, which makes its self-test run alone. They may also hold one line `# lane: free` or `# lane: alone`, which puts the script in the free lane or in the alone part of a check run (see Checks at the same time); a script with neither runs in the cargo lane. They may also hold one line `# limit: <n>`, a whole number of seconds from 1 to 999999999 with no leading zero, which raises the script's time limit (see below); a carriage return at its end does not count, as for the lane line, and a limit line after line 10 is not read.
- The driver starts it in the repo root as `sh <file>` or `sh <file> --self-test`, with no standard input, through `perl`, which gives it a process group of its own and sets INT and QUIT to their defaults. A background job of a shell starts with INT and QUIT ignored, and no shell can undo that, so without this start a script could not show what it does on an interrupt. A script therefore meets INT, QUIT, HUP and TERM as it does in the foreground on that system, in both kinds of run, several at a time and alone; on the windows runner the sh of Git Bash runs on after a QUIT that it sends itself, also in the foreground, so a script there does too. The driver fails with `FAIL run-ci-d (perl does not run; ...)` when `perl` does not run.
- A script that runs longer than its time limit fails with `FAIL <NN-name> (time limit <n> s)` in a check run and with `FAIL self-test:<NN-name> (time limit <n> s)` in a self-test run. The driver sends TERM to the script's process group, and KILL to the group 5 seconds later when a process of the group is still there. When the caller sets `CI_D_SCRIPT_LIMIT_S`, its value is the limit of every script. Without it, a script's limit is 1,200 seconds, or the number of a line `# limit: <n>` among its first ten lines when that number is higher, in both kinds of run.
- The margin of the limits. The default of 1,200 s has a margin of 1.5: a script whose longest measured hosted time passes 800 s names its own limit with `# limit: <n>`, at least 1.5 times that time, and its owner shows that the limit, with the other checks of the job as last measured, stays under the job's limit: the key `ci_gate_job_timeout_min` of `docs/baseline/r1-gate-bounds.txt`, in minutes. The driver reads neither that key nor any other source of the job's limit, so it takes a limit line above the job's limit, and a hang of such a script ends as the job's timeout with no named line. A process that the script started into a process group of its own is not ended at the limit. Today 12-test alone names one, `# limit: 1800`.
- When a script has ended, the driver ends what is left of its process group in the same way: in a check run at once, before it removes the `TMPDIR` and reads the tracked files; in a self-test run at the end of the run, for all self-tests at once, in one process: the driver waits up to 5 seconds for the groups that the self-tests left to end, then sends TERM to each group that is still there, and KILL 5 seconds later, so that a late line on standard error still reaches the log; the wait is the same for one such self-test as for several. A process that the script started into a process group of its own is not ended at the script's end.
- The driver sets `CI_D_REPO` (the repo root), `CI_D_JOB` (the job), `CI_D_ARTIFACTS` (the directory `target/ci-artifacts/<NN-name>/`, which the driver makes), `LC_ALL=C`, and `PATH` with the cargo bin directory first; in the form `--merge-gate` it sets `CI_D_MERGE_GATE=1`, and in every other form it takes that variable out of the environment. Every other variable of the caller whose name holds no lower-case letter passes through; the driver also sets `RUN_CI_D_WORKER` for its own use. The driver's own commands run on the caller's `PATH` without the cargo bin directory (an entry that is the same string as `$CARGO_HOME/bin` once trailing slashes are cut on both, or that `test -ef` finds to be the same directory), so a tool that a script puts there answers for the scripts after it and not for the driver. The driver runs its own git with no global git configuration (`GIT_CONFIG_GLOBAL=/dev/null` and no global attributes file) and with no variable of the caller whose name starts with `GIT_` (the names are read once when the driver starts); a setting that a script writes into the global configuration, or that the caller gives in such a variable, holds for the scripts and not for the driver's reads. A script gets the caller's environment as before, the `GIT_` names included. The system's git configuration, which carries `core.autocrlf` on the windows runner, comes from git's install prefix and is read as before.
- The last line that it prints on standard output and its exit status give the result:

  | Last line | Exit status |
  |---|---|
  | `PASS <NN-name>` | 0 |
  | `FAIL <NN-name> (<cause>)` | 1 |
  | `SKIP <NN-name> (<reason>)` | 77 |

  For any other status, or a last line that does not match the status, the driver prints `FAIL <NN-name> (exit <n>)`. In CI, where `CI=true`, a SKIP is a failure: a script installs the tool that it needs or fails.
- With `--self-test` it runs its own check on fixtures that it carries. At least one fixture must fail. Its last line is `PASS self-test:<NN-name> (<k> failing fixtures rejected)` with exit status 0, or `FAIL self-test:<NN-name> (<cause>)` with exit status 1. The driver fails a script whose `k` is 0.
- The driver gives it a `TMPDIR` of its own in both kinds of run, a new empty directory, and removes that directory after the script, whatever its status. Each script's `TMPDIR` is the one entry of a parent of its own, and those parents are the only entries of one directory that the driver makes for them, so `$TMPDIR/../..` is shared by all scripts. After a script the driver removes its `TMPDIR` alone: a script that closes its parent is named with the line below and the next script runs, and the parents go when the driver removes that directory at its exit. The driver keeps its own files (its reads of the tracked files, each script's output and status, the recap) in another directory, which holds no `TMPDIR`, so a script that writes the files of the directory that holds its `TMPDIR`, or of the directory above that, does not reach them. In a self-test run the driver removes a self-test's `TMPDIR` at the end of the run. The driver tries each removal up to three times, one second apart, so about 2 seconds in all, because on Windows a native program or a scanner can keep one removal from taking the whole directory. When the directory is still there after the third try, the script fails with `FAIL <NN-name> (its TMPDIR cannot be removed)`, or `FAIL self-test:<NN-name> (...)` in a self-test run. When the driver exits, it removes its own temporary directory.
- It writes only under a directory from `mktemp -d` with a template under `$TMPDIR` and under `CI_D_ARTIFACTS`. A script that makes a temporary directory anywhere else removes it by its own trap on EXIT, INT, TERM and HUP. It changes no tracked file and builds with `--locked`.
- The driver holds the rule on tracked files. It reads `git status --porcelain --untracked-files=no` against an index of its own, which it makes from HEAD and refreshes before the first script, so stat data that a script writes into the checkout's index hide no change; before the first script it also reads `git status` once against the checkout's own index, with `--no-optional-locks`, and a path that either read reports fails the run as a tracked file that differs from HEAD before the first script (that read goes into no later comparison, so no script is named for it); the paths whose entries in the checkout's index differ from HEAD (`git diff-index --cached`); the entries of `git ls-files -v` that are marked assume-unchanged or skip-worktree, the commit of HEAD, a hash of the settings that git reads for the checkout (the output of its own git's `config --list --show-origin`, files that the configuration includes and `config.worktree` with it; the driver keeps the hash alone and never prints or stores the listing, which holds the checkout's token), the content of `info/attributes` and the replace refs, before the first script, after each script of a check run, and after a self-test run as a whole, whose self-tests run at the same time. Each entry that a script or the run changed fails the run with `FAIL run-ci-d (<NN-name> changed a tracked file: <path>)` (`one of <NN-name>, <NN-name>` when other scripts ran beside it; see Checks at the same time), `FAIL run-ci-d (the step ci.d self-test changed a tracked file: <path>)` `FAIL run-ci-d (<NN-name> moved HEAD)` or `FAIL run-ci-d (<NN-name> changed the git settings of the checkout: <config, info/attributes or the replace ref>)`. A tracked file that already differs from HEAD before the first script fails the run with `FAIL run-ci-d (a tracked file differs from HEAD before the first script: <path>)`, and one marked assume-unchanged or skip-worktree with `FAIL run-ci-d (a tracked file is marked assume-unchanged or skip-worktree before the first script: <path>)`; no script is named for it, nor for a later change of such a file that leaves its line of `git status` as it was. After a script has changed a tracked file, the driver goes on with the scripts that run and that are still to run, on the checkout as it was left; the run fails, and a PASS line after such a line says nothing about the committed tree. What a process that a script started into a process group of its own writes later is seen at the next read and named for the script or scripts that ended since the read before it, which need not hold the writer; what it writes after the last read fails the next run before its first script, with no script named.
- It prints counts, sizes, times and booleans only, because the logs of CI are public.
- It does not depend on another script having run.

## The merge gate

A push and a pull request run the merge gate: the step `ci.d merge gate` of each job, `sh scripts/ci/run-ci-d.sh <job> --merge-gate`. A run of both jobs ends in under 1,200 s from its creation to the end of its last job. `scripts/merge-pr.sh` reads the pull_request run of a head, so the merge gate is what gates a merge. Before its checks the driver runs the red control (see Commands). Every other check that CI runs, each self-test that it runs and the step `Self-tests that commit in throwaway repositories` stand in the seven slices, which run on the schedule and in a run by hand (see The slices). The four repository checks of `AGENTS.md` (commit messages, changelog, line endings, own-source reads) are steps of their own and run on every event.

The merge gate reads what a pull request can change and no advisory database: 23-licences reads the allowed licences, the table of exceptions and `cargo deny check licenses sources`. The advisory databases of cargo and of npm change with no commit, so 25-advisories, which reads them by `cargo deny check advisories` with the committed `deny.toml` and by `npm audit` (no high and no critical advisory), stands in each of the seven slices of the macos job and in no line of `scripts/ci/merge-gate.txt` (see The slices).

Three tracked lists hold the merge gate:

- `scripts/ci/merge-gate.txt` names the checks. A line is a job, `macos` or `windows`, a blank and the name of a check; blanks before the job and a carriage return at the end do not count, and a blank line or a line whose first word starts with `#` is a comment. The driver reads the lines of its job and runs those scripts in lanes, as a check run does. Before any script starts it fails with `FAIL run-ci-d (scripts/ci/merge-gate.txt names <name>, which is no check of the job <job>)` for a name that is no script of that job, with `FAIL run-ci-d (scripts/ci/merge-gate.txt line <n> is not a job, macos or windows, a blank and the name of a check)` for any other line, with `FAIL run-ci-d (scripts/ci/merge-gate.txt names no check for <job>)`, and with `FAIL run-ci-d (scripts/ci/merge-gate.txt cannot be read)`. Before you add a line, name the seconds of the check in that job and what it protects.
- `scripts/ci/slow-tests.txt` names what 12-test skips in the merge gate. The driver sets `CI_D_MERGE_GATE=1` for the scripts of this form and takes the variable out of the environment in every other form. With neither that variable nor `CI_D_TEST_GROUP`, 12-test runs every test of the workspace; no run of CI uses that form. With `CI_D_TEST_GROUP=<letter>`, which the form `--slice` sets from the `tests` line of its slice and the form `--merge-gate` takes out of the environment, 12-test runs the tests that the list gives that group and no other test: the test targets of the packages of the group's `targets` lines, the test targets of its `target` lines in every package that has one, the unit tests of the packages of its `units` lines, the parts of its `test` lines in the unit tests of the package that each such line names, and the doc-tests when the line `doc-tests` holds the group. It then prints `form: the group <letter> of scripts/ci/slow-tests.txt, and no other test: ...` with the counts. With the variable set, 12-test runs `cargo test` in two calls: the unit tests of the packages that the list does not name with `units`, and the test targets that it names neither one by one with `target` nor by their package with `targets`; each call skips the tests whose name holds a part that the list names with `test`, and a third call runs the doc-tests unless the list holds the line `doc-tests`. A line `kept <package> <part>` brings one part back: a fourth call runs the unit tests of that package whose name holds the part, although a `units` line names the package, and prints `kept: the unit tests of <package> whose name holds: <part>` before them; after the run it prints `kept_count package=<package> part=<part> count=<n>`, the number of the tests of that call whose name holds the part and which passed, and fails when the number is 0, unless the word `macos` or `windows` follows the part, which marks a part whose tests one job alone has: the other job runs it, does not count it and prints `kept_not_counted package=<package> part=<part> (...)` in place of the count. It prints one line that names the list and the counts, `form: the merge gate; scripts/ci/slow-tests.txt names what this run skips: ...`, and writes `target/ci-artifacts/12-test/line-seconds.txt`, each line of the test run after the whole seconds since the run began, from which the slow tests of a run can be read.
- `scripts/ci/core-promises.txt` names the checks and the tests that hold one of the six core rules (the four promises, which are the secure-input guarantee, the key and the deletion of the store, what the capture takes and a billing amount; that nothing captured leaves the machine; and MIT-compatible licences only), each with its place: `gate` or `scheduled`, and for `scheduled` the reason. No check reads that list; a change of the other two lists updates it by hand.

## Limits that a script meets

- The rule on tracked files holds a script that writes the checkout by mistake. It does not hold a script that writes the driver's own files, whose directory stands beside the directory of the `TMPDIR`s (a script can learn its path without a search, for example from the path of its own standard error), an untracked `.gitattributes` in the work tree, which git reads in the driver's read as well and which can hide a re-encoding of the same size, a tool that it puts earlier on the `PATH` of the scripts after it (the cargo bin directory among them), the system's git configuration, `.git/info/grafts`, `.git/info/exclude`, a hook under `.git/hooks`, the job's environment files, or a change that is put back before the script ends; each of these is plain in a diff and is read at the landing.
- The windows job checks out the repository with depth 1, and the macos job checks it out with its whole history. A script that names the job `windows` reads no history: `git log` shows one commit, and a merge base or a diff against another commit fails there.
- A native Windows program reads `TEMP` and `TMP`, not `TMPDIR`, so what it writes there stays outside the `TMPDIR` that the driver removes. A signal of the driver does not reach a native Windows program, such as `cargo.exe`, that a script started; such a program can run on after the time limit and after an interrupt, and can hold the lock of the build directory.
- `target/ci-artifacts/12-test/tests.txt` holds the Running and Doc-tests lines and the test result lines of 12-test's `cargo test` run. It is no proof by itself that 12-test ran in the same driver run or passed: an earlier run can have left it, and a test's child can print lines of the same form. A script runs no crate's tests that 12-test runs, unless it reads that file first and runs them only when the file is missing, or its jobs line names windows alone (contract C16, point 18). 12-test runs in the alone part of a check run, after every script of the first part, so a script of the first part never finds the file of the same run: in a fresh checkout the file is missing when it reads it, and it runs the tests itself.

## Self-tests at the same time

With `--self-test` the driver runs the step in two parts. The first part runs every self-test that does not run alone, up to `CI_D_SELF_TEST_JOBS` at a time. Without the variable it runs as many as the machine has processors (`getconf _NPROCESSORS_ONLN`, else `NUMBER_OF_PROCESSORS`, else 1). The second part starts when every job of the first part has ended, and runs each self-test that runs alone, one after the other in the order of the run, with nothing beside it. The two parts took about 320 to 397 s off the self-test run of the windows job (verifier-1 of the CI-time run: 387 s on the one pair of one processor model, across runs, with the runner's speed taken out, and 292 to 397 s over all pairs; pr-review-1: about 320 to 370 s against each run's own self-test seconds; the raw fall on that pair is 476 s), from runs on processor models that GitHub draws by lot; 600 s off the job is not shown. A check run runs its scripts in lanes (see Checks at the same time).

- Each self-test writes its standard output and its standard error to files of their own. A self-test has ended when its script has exited and every process that holds its standard output has closed it, as in a run one at a time; its standard error does not hold the end. When a self-test and every self-test before it in the order of the run have ended, the driver prints its standard output, then its standard error as far as it is written, then its `seconds` line. A self-test that runs alone holds back the output of every self-test after it in the order of the run until it has run in the second part. So the log holds each script's lines together and in the order of the run, the byte order of the path (see The scripts root), whatever the number at a time and whatever the order of the starts, when the job reads both streams through one pipe; the workflow runs the driver without `2>&1`, and a runner that reads the two streams through two pipes can put a script's standard error after the next script's lines. What a process of a script writes on standard error after that print, in either kind of run, the driver prints before the recap, under the line `standard error of <NN-name> after it was printed:`.
- A self-test runs alone when its first ten lines hold `# self-test: alone`, or when its name is the first word of a line of `scripts/ci/self-test-alone.txt`. The driver then runs it in the second part of the run, after every other self-test has ended, and starts no other self-test until it has ended. A line of the list is the name, a blank and the reason; blanks before the name and a carriage return at the end do not count. A blank line, and a line whose first word starts with `#`, is a comment. The list holds the scripts that fail beside another and that the run which owns the list may not change; the owner of such a script moves it to its own header. The driver fails the run with `FAIL run-ci-d (scripts/ci/self-test-alone.txt names <name> without a reason)` for a line that holds a name and no reason, with `FAIL run-ci-d (scripts/ci/self-test-alone.txt names <name>, which is no script)` for a line whose name is no script of any job, and with `FAIL run-ci-d (scripts/ci/self-test-alone.txt cannot be read)` when the list is there and is no file that it can read.
- A self-test whose job in the driver ends without an exit status fails with `FAIL self-test:<NN-name> (it ended without an exit status)`.

## Checks at the same time

A check run runs its scripts in two parts. In the first part, the cargo lane runs every script that names no lane, one after the other in the order of the run, and beside it the free lane runs every script whose first ten lines hold `# lane: free`, in the order of the run, up to `CI_D_CHECK_JOBS` at a time. When every script of both lanes has ended and the driver has ended its group, removed its `TMPDIR` and read the tracked files, the second part runs the scripts whose first ten lines hold `# lane: alone`, one after the other in the order of the run, each with no other script of the run beside it. `CI_D_CHECK_JOBS` bounds the free lane alone. Without the variable the free lane runs as many as the machine has processors, counted as for `CI_D_SELF_TEST_JOBS`. A value that is not a whole number from 1 to 999999999 fails the run with `FAIL run-ci-d (CI_D_CHECK_JOBS=<value> is not a whole number from 1 to 999999999)`.

- Each script writes its standard output and its standard error to files of their own, and the driver prints them as it does in a self-test run: when a script and every script before it in the order of the run have ended, its standard output, then its standard error, then its `seconds` line. The recap holds the line of each script in the order of the run, and a script that fails stops no other. A script of the alone part holds back the output of every script after it in the order of the run until it has run in the second part, so a script that fails in the first part may print its lines near the end of the run. The lane line does not touch a self-test run: a self-test runs alone only by `# self-test: alone` or by scripts/ci/self-test-alone.txt.
- When a script has ended, the driver ends what is left of its process group, removes its `TMPDIR` and reads the tracked files at once, also while scripts before it in the order of the run still run. A change that it finds there names every script that ran since the last read, with the names in the order of the run: `FAIL run-ci-d (one of <NN-name>, <NN-name> changed a tracked file: <path>)`, and in the same way `one of <NN-name>, <NN-name> moved HEAD` and `one of <NN-name>, <NN-name> changed the git settings of the checkout`. That line stands in the recap after the line of the script at whose end the driver read the files; a change found at the end of a script of the alone part names that script alone. A change that a later read finds undone, after the driver reported it, is not reported again.
- A script names the free lane only when it keeps to all of this: it runs no cargo command (build, test, run, install, tree, metadata, fmt, clippy, deny or any other), so it never takes cargo's build lock; it binds no fixed port or socket path; it makes and reads no item of the login keychain; it writes nothing that another script reads or writes, and in the work tree it writes only under its `CI_D_ARTIFACTS`; it walks no directory that another script writes, such as `target/`; it depends on no other script; it counts no process of the whole machine; it starts no worker processes or threads of its own that keep several processors busy for more than a few seconds of a run with nothing beside it, so a model checker with several workers, as TLC is in the formal checks (36 to 187 s in the hosted run of main at b3eb47f6), names no lane, because on a hosted runner of 3 or 4 processors its workers take the processors that the cargo lane needs, while a tool that spreads a few seconds of work over threads or processes, as biome lint and node --test do, keeps to this; it installs no tool with a package manager; it runs no git command that writes the index of the checkout (add, update-index, stash, checkout --, reset, commit), because the driver reads the tracked files while it runs; and it leaves no process. A script that cannot be shown to keep to this names no lane.
- A script names `# lane: alone` when its verdict rests on a reading of this machine that another running script can move (a share of a processor, resident memory, a count of the machine's processes by name, or a time that it holds against a bound, a floor or a budget), or when it runs tests whose deadlines were set with the run to themselves, or when it changes a setting of the whole machine for the time of its run, such as a firewall rule that names no program or an audit setting. A script that names no lane is kept apart from cargo's builds and from nothing else. The driver keeps no other script of the run beside a script of the alone part; it does not keep away the runner's own services, nor a process that an earlier script left in a process group of its own.

## A signal to the driver

When INT, TERM or HUP reaches the driver, in either kind of run, it sends TERM to the process group of every script that runs or has ended without the driver having ended its group (in a self-test run that is every self-test that it started, the list that the end of the run walks), KILL 5 seconds later to a group that is still there, prints `FAIL run-ci-d (the step was interrupted by <signal>; every self-test that it started is ended)`, or `every script` in a check run, and exits with 130, 143 or 129. In a check run it first prints the standard output and the standard error of every script that it started and has not printed, in the order of the run. It names the scripts that it started, by their output; it does not name the scripts that never started, and it prints neither the recap nor the count line. A process that a script started into a process group of its own is not ended. The forms `--slice` and `--checks` hand the signal on to the run that they started, TERM for INT and for TERM and HUP for HUP, wait for it and exit with 130, 143 or 129.

What a self-test keeps to, so that it can run beside the others: it writes only under its `TMPDIR` and its `CI_D_ARTIFACTS`, depends on no other script's self-test, binds no fixed port or fixed path, counts no process of the whole machine, installs no tool with a package manager that another self-test also installs (two `brew install` runs at the same time clashed on one bottle directory in scratch run 43269049946), and leaves no process that holds its standard output or standard error. A self-test that cannot keep to this holds `# self-test: alone`.

## What the driver prints

1. The output of each script when it has ended, in the order of the run, then `seconds <NN-name> <n>`, the script's time in whole seconds, in both kinds of run. The `seconds` lines of scripts that ran at the same time overlap, so their sum is more than the time of the step.
2. One line for each script: the script's PASS, FAIL or SKIP line, or the driver's own FAIL line for it; and the driver's FAIL line for each tracked file that changed (see A script).
3. `ci.d <job>: <p> passed, <f> failed, <s> skipped`. With `--self-test` the line is `ci.d <job> self-test: <p> passed, <f> failed`.
4. The output of the lockfile guard, `git diff --exit-code HEAD -- Cargo.lock package-lock.json`, when a lockfile differs from HEAD, staged or not. The guard also compares the hash of each lockfile in the work tree with its blob in HEAD, so an index entry marked assume-unchanged hides no change.

## Exit status

| Status | Meaning |
|---|---|
| 0 | Every script that ran passed or skipped, at least one passed, and the lockfile guard passed. |
| 1 | A script failed, every script skipped, no script names the job, a NAME matches no script, `scripts/ci/merge-gate.txt` cannot be read or holds a line that the form `--merge-gate` refuses, a tracked file differs from HEAD (see A script), the lockfile guard failed, `CI_D_SCRIPT_LIMIT_S` is set to anything but a whole number from 1 to 999999999, or `perl` does not run. With `--merge-gate` also: the red control did not come out red. With `--slice` also: `scripts/ci/slices.txt` cannot be read, holds a line that is no slice, job, kind and name, names nothing for the slice and the job, or names a check that is no check of the job. With `--checks` also: a NAME is a check of neither job. In a check run also: `CI_D_CHECK_JOBS` is set to anything but a whole number from 1 to 999999999. With `--self-test` also: `CI_D_SELF_TEST_JOBS` is set to anything but a whole number from 1 to 999999999, or `scripts/ci/self-test-alone.txt` cannot be read, or a line of it names no script or gives no reason. |
| 130, 143, 129 | INT, TERM or HUP reached the driver, which ended every script that it had started. |
| 64 | Bad usage. |

The driver refuses an entry of a `ci.d` directory, prints `FAIL <name> (<cause>)` for it and counts it as failed in every job, when the entry is not a regular file (a directory or a symbolic link, also a dangling one), when its file name is not `NN-name.sh` (no `.sh` suffix, an upper-case suffix or a hidden name included), when its first ten lines do not hold exactly one `# jobs:` line and one `# rule:` line, when the `# jobs:` line names anything but `macos` and `windows`, when its first ten lines hold more than one `# lane:` line or a `# lane:` line that is neither `# lane: free` nor `# lane: alone` (a carriage return at its end does not count), when its first ten lines hold more than one `# limit:` line or one whose value is not a whole number from 1 to 999999999 with no leading zero (a carriage return at its end does not count), when git does not track it (`FAIL <NN-name> (git does not track it)`: `git ls-files` does not list it, as for a new script that is not added yet or a file that a self-test left in a `ci.d` directory for the next step), or when another script has the same name.

With no script for the job the driver prints `FAIL run-ci-d (no scripts for <job>)` and exits 1, also with `--self-test`.

## The slices

Seven slices hold what CI runs outside the merge gate. The workflow `ci` runs on the event `schedule` each day at 03:17 UTC, on the newest commit of main, and each cron line starts one slice, `mon` to `sun`. The step `Slice` of each job reads which cron line started the run (`github.event.schedule`) and hands the slice's name to the step `ci.d slice`, which runs `sh scripts/ci/run-ci-d.sh <job> --slice <slice>`. A run by hand (the event `workflow_dispatch`) takes the input `slice`, one of the seven names, and runs that slice as the run of its day does. With the input `checks`, names with blanks between them, it runs those checks alone in place of the slice, each with its self-test first (`--checks`): a name that is a check of the other job alone is skipped there with one line, and a name that is a check of neither job fails both jobs. No run of CI runs the whole table: a check or a self-test that neither `scripts/ci/merge-gate.txt` nor `scripts/ci/slices.txt` names runs in no run.

`scripts/ci/slices.txt` is the one list. A line is a slice, a job, a kind and a name. The kind `check` names a check, the kind `self-test` the self-test of a check, and the kind `tests` a group of `scripts/ci/slow-tests.txt` by its capital letter, which 12-test then runs in its group form (see The merge gate). The driver reads the lines of its slice and job and holds each name against the checks of the job before anything starts. It refuses a name that is no check of the job with `FAIL run-ci-d (scripts/ci/slices.txt names <name> for the slice <slice>, which is no check of the job <job>)`. Then it runs the slice's self-tests as a self-test run does, and after them its checks as a check run does, and exits 1 when one of the two failed.

A red slice shows in the repository's Actions list under the event `schedule`, and its jobs are checks on main's newest commit. No gate and no merge script reads a slice: `scripts/merge-pr.sh` reads only `pull_request` runs on the reviewed head. To mend a red run, read the failed job's log and fix the fault on a branch through a pull request, as any other fault; a run by hand of the slice, or of the one check with the input `checks`, on that branch shows the mend.

25-advisories stands in every slice of the macos job, and the table above leaves it out. Its FAIL line names the advisory's id. A red 25-advisories asks for a pull request of its own: update the lock to the version that mends the advisory, or, for cargo, add an ignore to `deny.toml` with its reason and a date (npm has no ignore here). Between two daily runs no run reads the databases, and a pull request that takes a yanked crate or leaves an ignore of `deny.toml` unused passes the merge gate; the next daily run shows it.

No run builds without the restored cache any more, so a break that only a restored cache hides shows in no run by itself. The cache goes when main's Rust caches are deleted, which GitHub's documentation lets an account with write access do on the Caches page under the repository's Actions tab or with the GitHub CLI (`gh cache delete`); main's next push run then builds from nothing and saves a new cache. It also goes when the restore key changes, by a change of the toolchain or of the prefix in the pinned prefix-key line, which is a ruled change of the pin.

The block `env:` at the top of `ci.yml` sets `CARGO_PROFILE_DEV_DEBUG` and `CARGO_PROFILE_TEST_DEBUG` to `limited` for both jobs, so each dev and test build of CI carries debug information without type or variable-level information (rustc's `-C debuginfo=limited`) in place of cargo's default for these profiles, which is full; the release profile, `Cargo.toml`, `.cargo/config.toml` and every build outside CI keep their settings.
With its default inputs, which `ci.yml` keeps, the Rust cache step hashes the rustc version and each variable whose name begins with `CARGO`, `CC`, `CFLAGS`, `CXX`, `CMAKE` or `RUST` into its restore key as well as its full key (`src/config.ts` of Swatinem/rust-cache at the pinned commit), so a change of the two values gives each job a new key: no event restores a Rust cache until a push run of main has saved one under the new key.
To take the setting back, take the block `env:` with its two lines out of `ci.yml`; the key changes again in the same way.

GitHub keeps at most 10 GB of caches for a repository, and past that it drops the cache read least lately. On 2026-11-22 the Rust cache of the windows job held 4,528 MB and that of the macos job 2,412 MB, so two of the windows job and one of the macos job do not fit, and a merge that changes a Cargo file gives each job a new key. A pull request's windows job then read the old windows cache, and GitHub dropped the new macos cache: every later macos job built from nothing, about 24 minutes.
So the last step of each job, `Keep one Rust cache`, runs `sh scripts/ci/keep-one-rust-cache.sh <job>` in a push run of main when the job is green and its Rust cache step found no cache with the full key (`cache-hit` is `false`). It deletes every cache whose key begins with `v0-rust-<job>-`, and the post step of the Rust cache step then saves the new one, so the repository holds one Rust cache for each job. A failed list or delete prints one line and fails no job.
For it `ci.yml` grants `actions: write` beside `contents: read`; it is the one step that holds the job's token in its environment (`GH_TOKEN`), an action whose input defaults to `github.token`, as actions/setup-node's does, still gets the token, and no checkout keeps it (`persist-credentials: false`).

The push runs of the branch main share one concurrency group, which cancels no run at work: GitHub lets the run at work end, keeps one pending run, the newest, and cancels the pending ones before it. So one macOS runner serves main at a time, and a burst of merges costs the run at work and one run of the newest commit; a pending run that is cancelled is no verdict on its commit. A pending run of main may wait a quarter hour for the run before it: that wait is by design and counts for no bound; the bound of 1,200 s is on each job and on a run from the start of its first job. A pull request has a group by its ref, in which a run of a newer head cancels the run of an older one; a tag's push and every other push have a group by their commit, and each run by hand has a group of its own.

The lint `scripts/r1/ci.d/17-workflow-lint.sh` pins the push filters, the seven cron lines of the schedule, the lines of the event `workflow_dispatch` when the file holds it, the two lines of the block `concurrency:`, each job's timeout line and each job's Rust cache step (the line `id: cache` may follow it). A change to those lines updates the pinned text in the same commit, by a ruling. The macos and windows jobs accept only `runs-on`, `timeout-minutes` and `steps`. A step condition is `always()`, or one of four that each belong to their steps alone: the condition of the step `Keep one Rust cache` (see above), the condition of the merge gate (`github.event_name == 'push' || github.event_name == 'pull_request'`) on the step `ci.d merge gate`, the condition of the slices (`github.event_name == 'schedule' || github.event_name == 'workflow_dispatch'`) on the steps `Slice` and `ci.d slice`, and the condition of the slice fri (`steps.slice.outputs.name == 'fri'`) on the steps `Self-tests that commit in throwaway repositories` and `Scripts and hook in a core.autocrlf=true clone`; no step may use `continue-on-error`. The lint does not read what a step runs, and so not which slice the step `Slice` gives a cron line: read changed step commands in the diff.

In a public repository GitHub switches a schedule off after 60 days without activity in the repository. The owner switches it on again on the repository's Actions page: select the workflow `ci`, then Enable workflow.

## The scripts root

The driver lists every entry of `scripts/*/ci.d/` in byte order of the path, and the hidden entries after all others, so `scripts/r1/ci.d/` runs before `scripts/r2/ci.d/`, and it runs each entry that is a regular file named `NN-name.sh`. When `CI_D_SCRIPTS` is set, it lists `$CI_D_SCRIPTS/*/ci.d/` instead. The root may be spelled `scripts`, `./scripts`, `scripts/`, with `/.` at its end, as an absolute path inside the work tree, as a path through a link to a directory of the work tree, from a working directory that is itself spelled through a link, under a caller's `CDPATH`, and under Git Bash in the form that `cygpath -m` gives: before it compares the entries with one listing of `git ls-files`, read with `core.quotePath=false`, the driver brings the root to the listing's form by its physical path (`cd -P` into the root, with `./` before a relative root, and `pwd -P`, against `pwd -P` of the top of the work tree), so a run directory named with a letter outside ASCII is read as tracked, and a root such as `x/../scripts`, with x a link, is read where its files lie, so an untracked script there is refused under a tracked name. When the cd fails, or the physical path is not under the top, the driver reads the root by its text. A root outside the work tree lists nothing that git tracks. A root that starts with two slashes is read as with one on macOS, while the sh of Git Bash reads it as a network path that names no directory of the work tree, so there the driver finds no script and answers `FAIL run-ci-d (no scripts for <job>)`. A run directory renamed by letter case alone, on a file system that ignores case, stays refused, because git lists it under its old name. This command shows that an empty set fails:

```sh
CI_D_SCRIPTS="$(mktemp -d)" sh scripts/ci/run-ci-d.sh macos
```

## Artifacts

A script saves what a reader of a failed run needs under `CI_D_ARTIFACTS`. The last step of each job uploads `target/ci-artifacts/` as the artifact `ci-artifacts-<job>`, also when the job failed.
