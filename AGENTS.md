# Halvo

Halvo is a desktop app for macOS and Windows that lets a person with no technical
background get work done through AI agents. This repository holds the Tauri 2 app in
`src-tauri/`, the capture crate in `crates/`, and the scripts and CI workflow that
build, check and release them.

## Rules

The rule table of this repository is below, and `CLAUDE.md` imports this file.

| Rule | Check | What the error tells you to do | Limits of the check, and the manual step that each leaves |
|---|---|---|---|
| No line of a commit message, of a squash message, or of the title or description of a pull request starts with `Co-Authored-By`, with `Generated with`, or with a tool trailer key and a colon (`Claude-Session`, `Agent-Logs-Url`, `Amp-Thread-ID`, `Assisted-by`), because the configured git user is the only author of a commit. | `scripts/check-commit-messages.sh` holds the one predicate, and `--help` states it. Five layers keep such a line out, in this order. (1) `.claude/settings.json` is tracked and tells Claude Code to add no attribution line. (2) `.githooks/commit-msg` gives early notice: it reads a message before git stores it. (3) `.githooks/pre-push` reads the stored messages of the commits that a push would add, and refuses the push. (4) The gate is the `Commit messages` step of the macOS CI job. It runs `scripts/ci-commit-messages.sh` on every push and pull request, which checks the settings file of layer 1 and the stored messages of the commits. (5) On a pull request the same step reads the title and the description. Layers 2 and 3 run in a clone where `sh scripts/prerequisites.sh` has set `core.hooksPath`. The commits reachable from `685d846` are exempt, because on 2026-11-09 the owner chose to keep the eight commits that already carried attribution lines. | It prints each commit and each line. For a commit that is not on main, remove the line with `git commit --amend` or `git rebase -i`, or reword prose so that it does not start with these words, and run the check again. For a commit that is already on main, do not amend or rebase: the owner decides between rewriting main and moving the exempt commit, with the reason recorded in this file. For the settings file, it names the key and the value that the key must have. | Layer 1 steers Claude Code only, and CI cannot see a user's own settings that override the file: do not set `attribution` in your own settings. Git does not run layer 2 for `--no-verify`, revert, cherry-pick, rebase, am and commit-tree, and below a diff header written by hand layer 2 passes an attribution line that a space indents or that follows a carriage return: layers 3 and 4 read the stored message. Layers 2 and 3 do not run in a clone without `core.hooksPath`, and `git push --no-verify` skips layer 3: run `sh scripts/prerequisites.sh` once in each clone. Layer 4 reads a commit after the push, so it cannot stop a squash commit that GitHub writes on main, and it does not read a description that is edited after the last push: merge with `scripts/merge-pr.sh`, which reads the squash message, the title and the description first. Layer 4 does not run for a push whose newest commit says `[skip ci]`: do not write that. No layer reads the author or the committer of a commit, or words spelled another way: read `git log --format='%an, %cn: %s' origin/main..HEAD` before you push. |
| A pull request is merged only with `sh scripts/merge-pr.sh <number> --head <full sha> --subject <text> --body-file <file>`. | The script reads the pull request with `gh` and refuses unless it is open, not a draft and mergeable, its head is the commit given with `--head`, check runs named `macos` and `windows` exist for that head and every check run on it succeeded, no review thread is unresolved, and the squash message, the title and the description pass the rule above. Then it squashes with `gh pr merge --squash --match-head-commit`, prints the merge commit with its author and committer, and runs the range check on that commit. `--dry-run` stops before the merge. `sh scripts/merge-pr.sh --self-test` proves each refusal with a stub `gh`. | Each refusal names the fact and the fix, for example to wait for a check, to resolve a thread, or to review the new head and pass it as `--head`. Exit 1 means that nothing was merged. Exit 3 means that the pull request is merged and its merge commit failed the range check or could not be checked: the row above says what to do with a commit on main. | Nothing on GitHub forces the script. A merge on the website or with `gh pr merge` goes through, and the push run of CI reports its commit only after the fact. Only a ruleset on main can stop it, and the owner sets that. Until then the manual step is the rule: merge no other way, and never pass `--admin`. |
| A pull request adds one line to `CHANGELOG.md` for each type of change it makes, at the end of the list under `## [Unreleased]`: `- <Type>: <text>`, with Type one of Added, Changed, Deprecated, Removed, Fixed, Security. The list has no `###` heading. | `scripts/check-changelog.sh` checks the structure of the file. With `--base <ref>` it also fails when no entry under `## [Unreleased]` is new compared with `<ref>`, except in the commit of a release, and when an entry sits in the section of a release that `<ref>` has without that entry. The `Changelog` step of the macOS CI job runs it on every push. On a pull request the base is the first parent of the merge commit that `actions/checkout` makes, so a rerun after the merge gives the same answer. `.gitattributes` gives the file git's union merge, so two branches that each add a line merge in a clone without a conflict. | It names the line and the fix. If it says that your entry sits in a release section, a release was made after you wrote the entry: move the line to the end of the list under `## [Unreleased]`, or delete it when the lint says that the same entry is already there. If GitHub shows a conflict in `CHANGELOG.md`, do not resolve it on GitHub: GitHub's own merge does not apply the union attribute, and `git merge origin/main` in a clone does. Run `git fetch origin` and `git merge origin/main` in a clone, then `sh scripts/check-changelog.sh --base origin/main`, and push. | The lint does not check that an entry is at the end of the list, or that each type of change has its entry: write them so yourself. The union merge keeps the lines of both sides. So `git revert` leaves the entry of the reverted change in the file when a later entry was added below it, and an entry that one branch rewords or deletes while another branch adds a line comes back as it was: after a revert or a merge, read the diff of `CHANGELOG.md` and delete such a line by hand. |
| A shell script or a git hook has LF line endings in every clone, also in a clone with `core.autocrlf=true`, the installer default of Git for Windows. | `.gitattributes` gives `*.sh` and `.githooks/*` the attributes `text eol=lf`. `scripts/check-line-endings.sh` reads the index. It fails when a tracked file that starts with an interpreter line has no `eol=lf`, when a file with `eol=lf` is stored with CRLF, and when such a file holds a carriage return inside a line. The `Line endings` step of the macOS CI job runs it. The last step of the Windows CI job clones the checkout with `core.autocrlf=true`, fails when a script comes out with CRLF, and commits through the hook there. | It names the file. It prints the line to add at the end of `.gitattributes` at the root (`/<path> text eol=lf`), or the command to run there and commit (`git add --renormalize -- <path>`). | It does not find a file that a script sources when that file has no interpreter line and no name that ends in `.sh`: give such a file a name that ends in `.sh`. |
