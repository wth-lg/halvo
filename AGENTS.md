# Halvo

Halvo is a desktop app for macOS and Windows that lets a person with no technical
background get work done through AI agents. This repository holds the Tauri 2 app in
`src-tauri/`, the capture crate in `crates/`, and the scripts and CI workflow that
build, check and release them.

## Rules

The rule table of this repository is below, and `CLAUDE.md` imports this file.

| Rule | Check | What the error tells you to do | Limits of the check, and the manual step that each leaves |
|---|---|---|---|
| No line of a commit message, of a squash message, or of the title or description of a pull request starts with `Co-Authored-By`, with `Generated with`, or with a tool trailer key and a colon (`Claude-Session`, `Agent-Logs-Url`, `Amp-Thread-ID`, `Assisted-by`), because the configured git user is the only author of a commit. | `scripts/check-commit-messages.sh` holds the one predicate, and `--help` states it. Five layers keep such a line out, in this order. (1) `.claude/settings.json` is tracked and tells Claude Code to add no attribution line. (2) `.githooks/commit-msg` gives early notice: it reads a message before git stores it. (3) `.githooks/pre-push` reads the stored messages of the commits that a push would add, and refuses the push. (4) The gate is the `Commit messages` step of the macOS CI job. It runs `scripts/ci-commit-messages.sh` on every push and pull request, which checks the settings file of layer 1 and the stored messages of the commits. (5) On a pull request the same step reads the title and the description. Layers 2 and 3 run in a clone where `sh scripts/prerequisites.sh` has set `core.hooksPath`. The commits reachable from `685d846` are exempt, because on 2026-11-09 the owner chose to keep the eight commits that already carried attribution lines. | It prints each commit and each line. For a commit that is not on main, remove the line with `git commit --amend` or `git rebase -i`, or reword prose so that it does not start with these words, and run the check again. For a commit that is already on main, do not amend or rebase: the owner decides between rewriting main and moving the exempt commit, with the reason recorded in this file. For a line in the title or the description of a pull request, remove the line on GitHub, then close and reopen the pull request: that starts a new run, and a re-run reads the old text. For the settings file, it names the key and the value that the key must have. | Layer 1 steers Claude Code only, and CI cannot see a user's own settings that override the file: do not set `attribution` in your own settings. Git does not run layer 2 for `--no-verify`, revert, cherry-pick, am and commit-tree, or for a commit that a rebase picks without a new message; `git rebase -i` runs it for a commit that it rewords. Below a scissors line and a diff header that someone wrote by hand, layer 2 passes an attribution line that a space indents or that follows a carriage return in a skipped line; below a diff header with no scissors line above it, layer 2 reads every line. Layers 3 and 4 read the stored message. Layers 2 and 3 do not run in a clone without `core.hooksPath`, and `git push --no-verify` skips layer 3: run `sh scripts/prerequisites.sh` once in each clone. `core.hooksPath` is the relative path `.githooks` and the settings file is a tracked file, so each checkout runs the hooks and the settings file of the commit that it has checked out. A checkout at an older commit has what that commit holds: at `d7b245a` the commit-msg hook runs the older `scripts/check-commit-messages.sh` of that commit, and there is no pre-push hook and no `.claude/settings.json`, and `a9d79ab` has no hook at all. Move such a checkout onto main before you commit there (`git merge origin/main` or `git rebase origin/main`). Layer 4 reads a commit after the push, so it cannot stop a squash commit that GitHub writes on main, and it does not read a description that is edited after the last push: merge with `scripts/merge-pr.sh`, which reads the squash message, the title and the description first. Layer 4 does not run for a push whose newest commit says `[skip ci]`: do not write that. No layer reads the message of an annotated tag: read it before you push the tag (`git cat-file -p <tag>`). No layer reads the author or the committer of a commit, or words spelled another way: read `git log --format='%an, %cn: %s' origin/main..HEAD` before you push. |
| A pull request is merged only with `sh scripts/merge-pr.sh <number> --head <full sha> --subject <text> --body-file <file>`. | The script reads the pull request with `gh` and refuses unless it is open, not a draft and mergeable, its head is the commit given with `--head`, the workflow runs on that head are green, no review thread is unresolved, and the squash message, the title and the description pass the rule above. The runs are green when, for each of the events push and pull_request, the newest workflow run on the head completed with success and the jobs `macos` and `windows` succeeded in it; an older run of the same event is not a gate. For a pull request whose head branch is in another repository the pull_request run alone is required. Then the script squashes with `gh pr merge --squash --match-head-commit` and reads the state of the pull request, whatever the exit code of `gh` was. Only when GitHub reports it merged does the script print the merge commit with its author and committer and run the range check on that commit. `--dry-run` prints every fact and stops before the merge. `sh scripts/merge-pr.sh --self-test` proves each refusal with a stub `gh`. | Each refusal names the fact and the fix, for example to wait for a run, to approve a run that waits for an approval, to close and reopen the pull request when no pull_request run starts or when a failed one read a line in the title or the description, to run the failed jobs of a run again when a runner failed, to resolve a thread, or to review the new head and pass it as `--head`. Exit 0 means merged, with a merge commit that passed the range check, or with `--dry-run` that every gate holds. Exit 1 means that a gate refuses and this run merged nothing. Exit 2 means that the script could not finish. Before the merge call this run merged nothing. After the merge call, when GitHub does not report the pull request as merged, the last line says that GitHub reports it as not merged, or that the script could not read its state and which command shows it. Exit 3 means that the pull request is merged and its merge commit failed the range check or could not be checked: the row above says what to do with a commit on main. Exit 64 means bad usage. | Nothing on GitHub forces the script. A merge on the website or with `gh pr merge` goes through, and the push run of CI reports its commit only after the fact. Only a ruleset on main can stop it, and the owner sets that. Until then the manual step is the rule: merge no other way, and never pass `--admin`. The script checks the squash message with the copy of `scripts/check-commit-messages.sh` in the checkout where it runs, so a checkout with a weaker predicate passes its own message: run the script from a checkout of main once main holds it. The script finds the workflow runs by the head commit, so it cannot tell which pull request a pull_request run belongs to when two pull requests share a head: read the run that it prints with `gh run view <run>`. It reads the newest run of each event, whatever workflow file started it, so with a second workflow file for an event it refuses when the newest run comes from a file without the jobs `macos` and `windows`, and it accepts the newest run of such a file when jobs of those names succeeded in it: keep the jobs of an event in one workflow file. It reads no check that an app other than GitHub Actions reports on the head: read those on the page of the pull request. |
| A pull request adds one line to `CHANGELOG.md` for each type of change it makes, at the end of the list under `## [Unreleased]`: `- <Type>: <text>`, with Type one of Added, Changed, Deprecated, Removed, Fixed, Security. The list has no `###` heading. | `scripts/check-changelog.sh` checks the structure of the file. With `--base <ref>` it also fails when no entry under `## [Unreleased]` is new compared with `<ref>`, except in the commit of a release, and when an entry sits in the section of a release that `<ref>` has without that entry. The `Changelog` step of the macOS CI job runs it on every push. On a pull request the base is the first parent of the merge commit that `actions/checkout` makes, so a rerun after the merge gives the same answer. `.gitattributes` gives the file git's union merge, so two branches that each add a line merge in a clone without a conflict. | It names the line and the fix. If it says that your entry sits in a release section, a release was made after you wrote the entry: move the line to the end of the list under `## [Unreleased]`, or delete it when the lint says that the same entry is already there. If GitHub shows a conflict in `CHANGELOG.md`, do not resolve it on GitHub: `git merge origin/main` in a clone applies the union attribute, and nobody has tested whether GitHub's own merge does. The one test so far is `git merge-tree --write-tree` in a bare clone, which reports a conflict for two branches that merge cleanly in a work tree. Run `git fetch origin` and `git merge origin/main` in a clone, then `sh scripts/check-changelog.sh --base origin/main`, and push. | The lint does not check that an entry is at the end of the list, or that each type of change has its entry: write them so yourself. The union merge keeps the lines of both sides. So `git revert` leaves the entry of the reverted change in the file when a later entry was added below it, and an entry comes back as it was when one branch rewords or deletes it while another branch adds a line next to it, as happens to the last entry of the list: after a revert or a merge, read the diff of `CHANGELOG.md` and delete such a line by hand. |
| Git checks out a shell script or a git hook with LF line endings, also in a clone with `core.autocrlf=true`, the installer default of Git for Windows. | `.gitattributes` holds the lines `*.sh text eol=lf` and `.githooks/** text eol=lf`. `scripts/check-line-endings.sh` reads the file content and the `.gitattributes` files from the index, not from the work tree, and it reads no attributes file of the user or of the system. It fails when a tracked file that starts with an interpreter line has no `eol=lf`, when a file with `eol=lf` is stored with CRLF, when a file that the attributes make text with `eol=lf` holds a carriage return inside a line or a NUL byte, and when a file with `eol=lf` under `text=auto` or `-text` holds a carriage return and no NUL byte. It also fails when the fix text of the last Windows CI step, the fixture of its own self-test or this row no longer quotes the lines of `.gitattributes` with `eol=lf` as that file has them. It stops with exit 2 when `info/attributes` of the clone holds an attribute line, because such a line wins over every `.gitattributes` file and no other clone receives it. The `Line endings` step of the macOS CI job runs it. The last step of the Windows CI job clones the checkout with `core.autocrlf=true`, fails when a script comes out with CRLF, and commits through the hook there. | It names the file. It prints the line to add at the end of the tracked `.gitattributes` file nearest to the file, which is the one at the root unless a directory above the file has its own (`/<path> text eol=lf`), or the command to run at the root and commit (`git add --renormalize -- <path>`). For a file with `-text` it prints both. For a file whose name a pattern would have to quote, it describes the line or the command and does not print it. For a carriage return inside a line or a NUL byte, it says to take the byte out. For a line in `info/attributes`, it says to move the line to a tracked `.gitattributes` file or to the attributes file of the user. | The lint does not find a file that a script sources when that file has no interpreter line, no name that ends in `.sh` and no place under `.githooks`: give such a file a name that ends in `.sh`. Git does not write a file again when a checkout leaves it unchanged. So a clone with `core.autocrlf=true` that checked the scripts out before `.gitattributes` held these lines keeps CRLF in each script that no later commit changed, with a clean `git status`, and the lint passes there, because it reads the index. The symptom, seen on macOS, is a commit that fails with `cannot exec '.githooks/commit-msg'`. To repair such a clone, commit or stash your changes, then run `git rm --cached -r -q . && git reset --hard` once: it empties the index and checks every tracked file out again. |
| No script reads its own source by line number. A script prints its help from a here-document. | `scripts/check-own-source-reads.sh` reads, in the work tree, every tracked file whose name ends in `.sh` or whose first line is an interpreter line. It splits each line into commands and words as sh does, and follows quotes, backslashes, command substitutions and redirections. A line fails when a command on it gets the path of the script and reads it by line number. The path is the parameter 0 alone, with or without quotes: `"$0"`, `"${0}"`, `$0` or `${0}`. The command gets it as an operand, on standard input, or from `cat` through one pipe. Such a command is `sed` with a script that starts with a line number, `head`, `tail`, or `awk` with `NR` or `FNR`, named alone, by a path such as `/usr/bin/sed`, in quotes, after a backslash, with `.exe` at its end, after assignments, or after `exec` or `command -p`. The `Own-source reads` step of the macOS CI job runs the self-test and the check. | It names the file and the line, and the fix: print the text from a here-document (`cat <<'EOF'`, the text, `EOF`), which holds the text and no line number. | The check reads one line at a time and expands nothing. It does not see a path that a variable holds or that is built from the parameter 0, as in `"$(dirname "$0")/name"`, a file descriptor that another line opened, a command that continues on another line, a reader that a parameter names, as in `${SED:-sed}`, a reader of another name, such as `gsed` or `perl`, a reader that another command starts, such as `env`, `nice` or `xargs`, standard input that a group, a loop or a function hands on, as in `{ head -n 3; } <"$0"`, a script that comes through more than one pipe, or, in `sed`, an address that a variable holds, a line number after the first command of a script, as in `'/x/p;3p'`, and a read by a pattern: when you change how a script prints its text, read the line yourself. It cannot tell code from text and reads every line as code, so it also refuses a line of a here-document, or of a quoted string that began on a line above, when such a read is a command of that line: write that text another way. |
