- Added: (capture run, derived-key) `DataDirStore::derived_store_key`, the one call that hands the daemon the key of the derived store: on a first ask it makes 32 random bytes, wraps them under the root that store/store.key names with the label `derived`, makes derived/ (0700) and publishes derived/master.key (0600) in the store's key-file form, create-only by a hard link from a temporary name of its own, and a later ask, or one whose link lost a race, unwraps that file and answers the same key. It opens no database and takes no lock, never replaces or removes a key file, and answers `DerivedKeyFault`, a variant for each failure (no capture store, a store.key or a master.key that does not read, a master.key that names another root, a root that is gone, damaged, denied or locked, a custody kind that the build does not handle, an I/O fault), with nothing made when the capture store or its root does not answer; it works in a data directory reached through a link too. A delete of everything destroys that root, so the key cannot be read after it.
- Fixed: (capture run, derived-key, pr-review-86 F1) In a data directory reached through a link, which halvo-control's check accepts as Linked, the offline delete of everything answered 1 with no line on standard error, wrote no intent (its line read `intent=failed`) and left the mark store_made set, and a start removed nothing of a store that an intent named, because `DataDirStore::remove_durably`, `sync_folder` and the host's delete, and the delete's write of the intent and clear of the mark, opened or handed on the data directory by its own name and followed no link there. They now open the directory that a link at that one name leads to, which `DataDirStore::resolved_path` hands over, and every other path of the store still follows no link at its last part.
